# Передача проекта APEXWOLT B2B для Claude

Актуально на **1 октября 2026 года**.

## 1. Что это за проект

APEXWOLT B2B — премиальная B2B-платформа для корпоративного выбора инструмента, формирования заявки и дальнейшей работы с закреплённым менеджером. Это не интернет-магазин с оплатой на сайте.

Основное направление дизайна:

- белая композиция с большим количеством воздуха;
- мягкие glass-панели;
- один акцентный синий цвет;
- локальный шрифт Golos Text;
- минималистичные линейные SVG-иконки;
- фоновый ролик с покадровым управлением от скролла;
- визуальная подача уровня Apple, но не буквальное копирование.

### Важно: большая часть функций пока демонстрационная

- Настоящей авторизации, БД и серверной части нет.

- Заявка хранится локально и показывает демонстрационный успешный экран; менеджеру реально не отправляется.
- Избранное, сравнение и часть состояния используют `localStorage`.
- Скрытие цен — визуальный auth-gate, а не защита данных на сервере.
- Видеообзоры и внешние площадки пока заглушки.
- Ассортимент и остатки демонстрационные.
- Юридические тексты нельзя считать финальным заключением юриста.

## 4. Критическая логика фонового видео

В `dist/script.js` сейчас задана шкала:

```js
const sectionFilmStops = [
  { selector: '.hero', time: .08 },
  { selector: '#catalog', time: 3.08 },
  { selector: '.service-intro', time: 6.16 },
  { selector: '.partner-support', time: 9.20 },
  { selector: '#platform', time: 12.24 },
  { selector: '.video-reviews', time: 17.28 },
  { selector: '#account', time: 20.10 },
  { selector: '#contacts', time: 20.10 }
];
```

Намерение пользователя:

- на самих разделах ролик должен быть близок к резкому статичному ключевому кадру;
- в пространстве между разделами анимация плавно проигрывается скроллом;
- каталог держит второй ключевой кадр;
- следующий сервисный раздел — третий;
- следующие разделы последовательно сдвинуты дальше по ролику;
- переходы нельзя телепортировать;
- категории каталога на главной остаются статичными картинками и ведут на отдельную страницу;
- на mobile эффект сохраняется, но используется облегчённый файл и минимум тяжёлых фильтров.

В локальном preview есть Blob-fallback для серверов без корректного HTTP Range. Не удалять его без полноценной замены.

После любых изменений проверить:

1. хиро резкий после загрузки;
2. кадр каталога не перескакивает вперёд;
3. ролик следует скроллу в обе стороны;
4. нет белых разрывов;
5. mobile не загружает desktop-файл;
6. `prefers-reduced-motion` не ломает страницу.

## 5. Следующий план работ

### Этап A — зафиксировать и проверить текущую основу

1. Сделать полный визуальный аудит текущей production/local версии.
2. Составить короткий список регрессий desktop/mobile, ничего глобально не переделывая.
3. Проверить Git diff и предложить безопасную точку фиксации текущего состояния.
4. Не коммитить и не деплоить без разрешения пользователя.

### Этап B — сделать заявку реально рабочей

Сначала уточнить у пользователя канал передачи менеджеру: Telegram, email, CRM/webhook или комбинация. Затем:

1. Добавить форму контактов организации и ответственного лица.
2. Валидировать состав заявки, количество, контактные данные и согласия.
3. Отправлять заявку через безопасный backend/serverless endpoint, а не из клиентского JS с секретом.
4. Добавить идентификатор заявки, состояния загрузки, ошибку, повтор и подтверждение.
5. Не называть действие покупкой или оплатой.

### Этап C — реальная авторизация и личный кабинет

Нужно приблизиться по функциональной насыщенности к кабинету конкурента `b2b.utake.ru`, но сохранить более чистый интерфейс.

Необходимые сущности:

- организация и реквизиты;
- пользователи и приглашения;
- роли: закупщик, руководитель, бухгалтер, администратор;
- закреплённый менеджер;
- заявки и их статусы;
- повтор заказа;
- документы и выгрузки;
- персональный прайс и договорные условия;
- POS-материалы и сервисные запросы;
- интеграции, API/REST и обмен файлами как отдельный будущий модуль.

Сначала предложить архитектуру backend под будущий Yandex Cloud. Не имитировать безопасность только CSS-размытием: приватные цены и данные нельзя отдавать неавторизованному клиенту.

### Этап D — полный ассортимент и автоматизация Excel

Изначальная цель пользователя — регулярно обновлять сайт из Excel-файла с товарами, фотографиями, характеристиками и ценами.

Правильный порядок:

1. Вместе с пользователем утвердить схему Excel: SKU/артикул, категория, название, описание, характеристики, остаток, срок, публичные и закрытые цены, изображения, статус публикации.
2. Сделать детерминированный импортёр с валидацией, отчётом ошибок и dry-run.
3. Хранить каталог в нормализованном источнике данных, а не в массиве внутри `catalog.js`.
4. Добавить обработку изображений по шаблону: удаление/проверка фона, единый canvas, padding, WebP/AVIF, превью.
5. Только после стабильного импортёра добавлять плановый агент/автоматизацию.
6. Обязательны журнал изменений, резервная версия и возможность отката. Агент не должен бесконтрольно публиковать повреждённые данные.

### Этап E — каталог

- Заменить демонстрационные товары реальным ассортиментом.
- Сохранить два режима: подробный B2B-список и сетка по 4 карточки на desktop.
- Показывать публично: фото, название, артикул, основные характеристики, наличие/срок в допустимом объёме.
- После авторизации: персональные цены и другие закрытые коммерческие показатели.
- Проверить сортировки, поиск по артикулу, категориям и названию.
- Сделать реальными избранное, сравнение и заявочную корзину.

### Этап F — сервисы и контент

- Подставить реальные ссылки и превью видеообзоров для YouTube/VK Видео/Rutube, когда пользователь их даст.
- Уточнить реальные условия бесплатной продукции для стенда и программы мотивации.
- Проверить все формулировки производства и сервиса с владельцем бизнеса.
- Добавить отзывы/кейсы только после получения настоящих материалов.

### Этап G — безопасность, юридическая часть и Yandex Cloud

- Подключить Yandex SmartCaptcha к регистрации, заявке и подписке, когда появится backend и ключи.
- Добавить consent logging для рассылки и обработки данных.
- Финально сверить реквизиты и юридические тексты с официальным B2C-сайтом и юристом.
- Настроить CSP и отказаться от CDN GSAP/Lenis либо явно разрешить проверенные домены.
- Перед переносом на Yandex Cloud подготовить environment variables, логирование, мониторинг и резервное копирование.

### Этап H — финальный QA

- Chrome/Edge/Safari, desktop/tablet/mobile.
- Медленная мобильная сеть и холодный кэш.
- Скролл-видео, отсутствие layout shift и читаемость текста.
- Клавиатура, focus-visible, формы и reduced motion.
- Проверка 404, внутренних ссылок, юридических страниц, cookie и SEO metadata.
- Lighthouse и ручная проверка реальным телефоном.

## 6. Известные продуктовые решения

- Категории остаются на главной, но открываются отдельной страницей каталога.
- На главной четыре категории в строке на широком desktop, если ширина позволяет; адаптив не должен сжимать карточки до нечитаемости.
- Поисковик категорий должен быть заметным, но с мягким размытым синим свечением без чёткой границы.
- Избранное, сравнение и профиль — компактные иконки возле заявки.
- Стекло должно быть мягким и дозированным: видео и товар должны оставаться видны.
- Производство — крупный акцент; остальные преимущества партнёров — более компактные плитки.
- Блок видеообзоров остаётся, но пока без нового сгенерированного фонового видео.
- Рассылка планируется, поэтому заготовку не удалять; рекламное согласие должно быть отдельным.
- Контакт разработчика: LMH Studio, Telegram `https://t.me/aleks1y_m`.

Локально можно поднять статику из корня репозитория:

```powershell
npx serve dist -l 4173
```

Production уже связан с Netlify. Команда ниже — только после явного разрешения пользователя и полного QA:

```powershell
npx netlify-cli deploy --dir=dist --prod
```

Нельзя делать production deploy автоматически после обычной правки.

## 9. Как безопасно передать работу

- Не запускать Codex и Claude на одновременное редактирование одних и тех же файлов.
- Перед переключением всегда смотреть `git status --short` и записывать, что было изменено.
- Лучше работать маленькими согласованными этапами и после каждого проверять diff.
- Для параллельной работы использовать отдельную Git-ветку или worktree; не давать двум агентам писать в одну рабочую копию одновременно.
- После возвращения к Codex первым делом показать ему этот handoff и свежий Git diff.
